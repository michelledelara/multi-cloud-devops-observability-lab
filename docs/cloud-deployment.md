# Cloud deployment and state

Run commands from the repository root unless indicated otherwise. Use existing accounts and private credentials outside the repository. These procedures create real resources only when you execute an apply or deploy command.

## Azure

Install Azure CLI and Terraform. Authenticate and verify the target:

```bash
az login
az account show
az account set --subscription YOUR_SUBSCRIPTION_ID
cp terraform/azure/terraform.tfvars.example terraform/azure/terraform.tfvars
```

Edit `terraform.tfvars` with your subscription ID and region. Credentials are not stored in this file. The provider uses your Azure CLI session. The identity needs permission to manage the target network/resource group; registration of the Microsoft.Network resource provider may require subscription-level permissions in a restricted subscription.

```bash
terraform -chdir=terraform/azure init
terraform -chdir=terraform/azure fmt -check
terraform -chdir=terraform/azure validate
terraform -chdir=terraform/azure plan -out=lab.tfplan
terraform -chdir=terraform/azure apply lab.tfplan
terraform -chdir=terraform/azure output
```

Resources: one Resource Group, VNet, subnet, NSG and association. The NSG allows TCP/8080 from VirtualNetwork and denies other inbound traffic with explicit rules. Outbound NSG defaults remain in place. This does not provision a VM, public IP, NAT gateway or AKS cluster.

Cleanup:

```bash
terraform -chdir=terraform/azure plan -destroy -out=destroy.tfplan
terraform -chdir=terraform/azure apply destroy.tfplan
```

## OCI

Install OCI CLI and Terraform. Configure your own OCI API signing credentials with `oci setup config`, keeping the signing key and `~/.oci/config` outside the repository. Use an existing compartment where your identity has permission to manage the lab's virtual-network resources.

```bash
oci iam region list
cp terraform/oci/terraform.tfvars.example terraform/oci/terraform.tfvars
```

Set the compartment OCID, region and config profile in `terraform.tfvars`.

```bash
terraform -chdir=terraform/oci init
terraform -chdir=terraform/oci fmt -check
terraform -chdir=terraform/oci validate
terraform -chdir=terraform/oci plan -out=lab.tfplan
terraform -chdir=terraform/oci apply lab.tfplan
terraform -chdir=terraform/oci output
```

Resources: VCN, regional private subnet, empty route table and custom security list. The subnet explicitly uses this list, avoiding implicit reliance on the default security list. TCP/8080 is allowed from the VCN; egress is limited to the VCN. No internet/NAT gateway, VM or OKE cluster is provisioned.

Cleanup:

```bash
terraform -chdir=terraform/oci plan -destroy -out=destroy.tfplan
terraform -chdir=terraform/oci apply destroy.tfplan
```

## Terraform state

The default is local state, suitable for a single-operator lab. Never commit state, saved plans or credentials. Commit `.terraform.lock.hcl` when generated by `terraform init`; it records provider selections and checksums. Provider versions are pinned intentionally. Validate upgrades in CI before updating the constraints and lock files.

For shared Azure state, provision a storage account and private blob container separately, configure an identity with access to the blob, then add:

```hcl
terraform {
  backend "azurerm" {}
}
```

Copy `backend.hcl.example` to a local backend config and set the existing resource names. Run `terraform init -migrate-state -backend-config=backend.hcl` from `terraform/azure`. Review the state migration prompt. Use Azure AD authentication and state locking supported by that backend. Do not configure OCI and Azure with the same state key. This repository does not auto-provision or migrate a shared backend.

## AWS CloudFormation

Install AWS CLI, authenticate with your own profile/SSO session, and verify identity and region:

```bash
aws sts get-caller-identity
aws configure get region
aws cloudformation validate-template --template-body file://cloudformation/aws/template.yaml
aws cloudformation deploy --stack-name multicloud-lab --template-file cloudformation/aws/template.yaml --parameter-overrides ProjectName=multicloud-lab --no-execute-changeset
```

Inspect the proposed change set in the CloudFormation console. Execute it there after review, or run the same `deploy` command without `--no-execute-changeset` to create and execute a change set.

Resources: VPC, private-addressed subnet, security group, seven-day log group, 5xx metric filter, CloudWatch alarm and dashboard. There is no compute resource and no automatic export from the local API to AWS.

### Send application logs to CloudWatch

Create the stack first, generate traffic in Compose, then export recent JSONL:

```bash
mkdir -p evidence/runtime
docker compose exec -T api sh -c 'tail -n 100 /var/log/lab/app.jsonl' > evidence/runtime/app.jsonl
python scripts/cloudwatch_ship.py evidence/runtime/app.jsonl --region YOUR_AWS_REGION
```

The script requires `logs:CreateLogStream` and `logs:PutLogEvents` on the lab log group. It sends a bounded batch using the original application timestamps. Send recent data; CloudWatch enforces event age and time-span limits. This is a manual integration path with no hidden background transfer.

The metric filter maps `status >= 500` to `ServerErrors` in the `multicloud-lab/API` namespace. The alarm requires at least five errors in each of two one-minute periods. CloudWatch needs ingested matching log events; provisioning the stack alone does not populate metrics. The dashboard and Logs Insights examples are in `observability/cloudwatch/` and the stack template.

Cleanup:

```bash
aws cloudformation delete-stack --stack-name multicloud-lab
aws cloudformation wait stack-delete-complete --stack-name multicloud-lab
```

This deletion also removes the stack's lab log group and its retained log events. Export evidence you need before deletion.

## Resource consumption

No always-on cloud compute, public IP or NAT gateway is created by these definitions. CloudWatch log ingestion, custom metrics, alarms and dashboards can incur charges under the account's current pricing and usage. Check your account's cost controls, then remove resources through the owning IaC tool. Local `docker compose down` is independent of cloud teardown.
